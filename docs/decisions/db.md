# DB設計の約束

DBは MySQL（手元はDocker）＋ Drizzle ORM。ER図（`docs/er.md`）はこのファイルを前提に書く。

## DBの種類

- MySQL を使う
- インターン先と同じなので、インターンと個人開発の学びが互いに効き、聞ける相手もいるため

## 「確定は1件だけ」の守り方

- 依頼テーブルに「確定した講師」の列を1つ持たせる
- MySQLには部分一意インデックスがないため。列が1つなら、構造上1人しか入らない

## 申し出の重複を防ぐ

- 申し出テーブルは（依頼, 講師）の組で一意制約を付ける。同じ人の二重申し出を、アプリではなくDBで防ぐため
- 取り下げた申し出はレコードごと消すので、取り下げてからもう一度申し出ても、この一意制約とはぶつからない（[business-rules.md](business-rules.md)）
- 同じコマへの二重の依頼をDBでどう防ぐかは未決（[open-questions.md](open-questions.md) の「同じコマへの二重の依頼を、DBでどう防ぐか」）

## 日時の型

- 日時は整数（`bigint`）で持つ。時限の開始・終了時刻は時限表テーブルに置く
- MySQLの `DATETIME` はタイムゾーンを持たず、`TIMESTAMP` は2038年までしか表せないため。整数ならタイムゾーンの扱いで迷わない
- 秒かミリ秒かは未決（[open-questions.md](open-questions.md) の「日時の単位」）。決めたら全体で統一する

## 状態の変更（同時押し）

- 状態の変更（選ぶ・取り消す）は条件付きUPDATEで行う。条件には授業の開始時刻も含める（期限切れの依頼はAPIでも操作できないため。[business-rules.md](business-rules.md)）
- 更新件数（affected rows）が0のときは、今の状態を読み直す。自分の操作がもう反映されていれば成功（二重クリックなど。冪等性）、違えば「先に誰かが変えた」として扱う
- MySQLには `UPDATE … RETURNING` がないため。条件付きUPDATEなら、1文で「確認と更新」を同時に行える
- 例：`UPDATE 依頼 SET 状態='成立', 確定した講師=? WHERE id=? AND 状態='申し出あり'`
- 取り消しは、条件付きUPDATE1文で行い、明示的なトランザクションは使わない。1行の更新だけで済むため
- 取り下げと申し出（「募集中→申し出あり」）も同じ守り方にするかは未決（[open-questions.md](open-questions.md) の「同時操作の守り方」）。申し出はINSERTなので、「状態を確認してから記録する」の間に割り込まれる可能性がある（`docs/concurrency-cases.md` のケース4・5）

## 分離レベル

- MySQL（InnoDB）の既定の Repeatable Read を前提にし、同時実行のテストもその前提で書く
- PostgreSQLの既定（Read Committed）とロックのかかり方が違うため。MySQLは範囲にもロックをかける（ギャップロック）ので、思わぬところで待ちが起きることがある

## Better Auth のテーブル

- Better Auth が作るテーブル（`user`・`session`・`account`・`verification`）は、ライブラリ経由でだけ書き換える
- 例外：MVPでの役割の付与（教室長・開発者）は、開発者がスクリプトで行う（[auth.md](auth.md)、スクリプトの約束は [operations.md](operations.md)）
- 役割と承認状態の持ち方は [auth.md](auth.md)

## `user.email` の中身

- MVPでは全員がLINEで入るので、`user.email` はすべて仮アドレスになる。メールとパスワードのログインを足すと、本物のメールが混ざる
- 仮アドレスは画面に出さない
- LINEで入る人を見分ける鍵は、`account` テーブルの「プロバイダー＋ID」の組

## 制約の置き場所

- 制約はアプリではなくDBに書く（一意制約、外部キー、NOT NULL など）
- アプリのバグや同時実行があっても、DBが最後に守るため

## 生徒の情報

- 生徒の情報を持つ列やテーブルは作らない（理由は [business-rules.md](business-rules.md)）

## ER図で確かめること（チェックリスト）

- [ ] 依頼テーブルに「確定した講師」の列がある
- [ ] 申し出テーブルに（依頼, 講師）の一意制約がある
- [ ] 日時が整数で、単位が決まっている
- [ ] `user` と依頼・申し出の関係、`user` の役割・承認状態の列がある
- [ ] 時限表テーブルがある
- [ ] 生徒の情報を持つ列やテーブルがない
