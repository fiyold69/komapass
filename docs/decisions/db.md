# DB設計の約束

DBは MySQL（手元はDocker）＋ Drizzle ORM。ER図（`docs/er.md`）はこのファイルを前提に書く。

## 決まっていること

### DBの種類

- 決定：MySQL
- 理由：インターン先と同じ。インターンと個人開発の学びが互いに効き、聞ける相手もいる
- 決めた日：2026-10-12
- 影響：PostgreSQL前提だった設計のうち、下の4つ（確定は1件だけ、同時押し、日時の型、分離レベル）のやり方が変わった

### 「確定は1件だけ」の守り方

- 決定：依頼テーブルに「確定した講師」の列を1つ持たせる
- 理由：MySQLには部分一意インデックスがない。列が1つなら、構造上1人しか入らない
- 決めた日：2026-10-12

### 申し出の重複を防ぐ

- 決定：申し出テーブルは（依頼, 講師）の組で一意制約を付ける
- 理由：同じ人の二重申し出を、アプリではなくDBで防ぐ
- 決めた日：2026-10-12
- 未決：申し出の取り下げを入れる場合、この一意制約とぶつかる可能性がある（[open-questions.md](open-questions.md)）

### 日時の型

- 決定：日時は整数（`bigint`）で持つ。時限の開始・終了時刻は時限表テーブルに置く
- 理由：MySQLの `DATETIME` はタイムゾーンを持たず、`TIMESTAMP` は2038年までしか表せない。整数ならタイムゾーンの扱いで迷わない
- 決めた日：2026-10-12
- 未決：秒かミリ秒か（[open-questions.md](open-questions.md)）。決めたら全体で統一する

### 状態の変更（同時押し）

- 決定：状態の変更（選ぶ・取り消す）は条件付きUPDATEで行い、更新件数（affected rows）が0なら「先に誰かが変えた」として扱う
- 理由：MySQLには `UPDATE … RETURNING` がない。条件付きUPDATEなら、1文で「確認と更新」を同時に行える
- 例：`UPDATE 依頼 SET 状態='成立', 確定した講師=? WHERE id=? AND 状態='申し出あり'`
- 決めた日：2026-10-12
- 追記（2026-10-13）：期限切れの依頼はAPIでも操作できないと決めたので（[business-rules.md](business-rules.md)）、条件には授業時刻も含める（開始か終了かは未決）
- 未決：取り下げ、申し出（「募集中→申し出あり」）も同じ守り方にするか。申し出はINSERTなので、「状態を確認してから記録する」の間に割り込まれる可能性がある（`docs/concurrency-cases.md` のケース4・5）

### 分離レベル

- 決定：MySQL（InnoDB）の既定の Repeatable Read を前提にし、同時実行のテストもその前提で書く
- 理由：PostgreSQLの既定（Read Committed）とロックのかかり方が違う。MySQLは範囲にもロックをかける（ギャップロック）ので、思わぬところで待ちが起きることがある
- 決めた日：2026-10-12

### Better Auth のテーブル

- 決定：Better Auth が作るテーブル（`user`・`session`・`account`・`verification`）は、ライブラリ経由でだけ書き換える。役割と承認状態は `user` テーブルに列を足して持ち、利用者が自分で書き換えられない設定にする（[auth.md](auth.md)）
- 例外：役割の付与とパスワードの再設定は、開発者がスクリプトで行う（[auth.md](auth.md)）
- 決めた日：2026-10-12（スクリプトの例外は 2026-10-13）

### `user.email` の中身

- 決定：`user.email` には、本物のメール（教責・開発者）と仮アドレス（LINEの講師）が混ざる。仮アドレスは画面に出さない。LINEの講師を見分ける鍵は `account` テーブルの「プロバイダー＋ID」の組
- 決めた日：2026-10-13（関連：#16）

### 制約の置き場所

- 決定：制約はアプリではなくDBに書く（一意制約、外部キー、NOT NULL など）
- 理由：アプリのバグや同時実行があっても、DBが最後に守る
- 決めた日：2026-10-12

### 生徒の情報

- 決定：生徒の情報を持つ列やテーブルは作らない（[business-rules.md](business-rules.md)）
- 決めた日：2026-10-11

## ER図で確かめること（チェックリスト）

- [ ] 依頼テーブルに「確定した講師」の列がある
- [ ] 申し出テーブルに（依頼, 講師）の一意制約がある
- [ ] 日時が整数で、単位が決まっている
- [ ] `user` と依頼・申し出の関係、`user` の役割・承認状態の列がある
- [ ] 時限表テーブルがある
- [ ] 生徒の情報を持つ列やテーブルがない
