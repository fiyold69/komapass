# 業務ルール

代講の依頼から成立までのルールと、MVPの範囲。ユーザーストーリー（`docs/user-stories.md`）、状態遷移図、ER図は、このファイルを前提に書く。

## 用語

| 用語 | 意味 |
| --- | --- |
| コマ | 「日付＋時限の番号」で表す授業の枠 |
| 依頼 | 講師が「このコマに出られない」と代講を募集すること |
| 申し出 | 他の講師が「代われます」と手を挙げること |
| 成立 | 依頼した講師が、申し出た人から1人を選んだ状態 |
| 教室長 | 教室の責任者（役割名は `admin`） |

## 決まっていること

### 役割

- 決定：講師（`teacher`）、教室長（`admin`）、開発者（`superadmin`）の3つ。1人に役割は1つで、教室長は講師を兼ねない
- 理由：役割の持たせ方が単純になる
- 決めた日：2026-10-11

### コマの定義

- 決定：コマは「日付＋時限の番号」だけで表す。時限の開始・終了時刻は「時限表」テーブルに置く。生徒の情報は一切持たない
- 理由：代講の調整に生徒の情報は要らない。持たなければ漏れない。時限表は期限切れの判定に使う
- 決めた日：2026-10-11
- 時限表の入れ方：MVPでは、開発者がスクリプトで入れる。教室長が画面で入れる機能はMVPの後。決めた日：2026-10-18

### 依頼の状態

- 決定：募集中 → 申し出あり → 成立。募集中と申し出ありからは、依頼者が取り消せる
- 理由：MVPに必要な最小の流れ。期限切れは状態として持たない（下の「期限切れ」）
- 決めた日：2026-10-11（取り消しをMVPに入れたのは 2026-10-12）

### 依頼の制限

- 決定：同じ講師が、同じコマ（日付＋時限）に出せる有効な依頼は1つだけ。「有効な依頼」は、取り消していない依頼（募集中・申し出あり・成立）のこと
- 理由：二重に依頼を出すと、申し出が分かれて混乱する
- 補足：DBで防ぐのが難しければ、MVPでは二重に出せる状態でもよい（守り方は [open-questions.md](open-questions.md)）
- 決めた日：2026-10-18

### 依頼の一覧を見られる人

- 決定：講師と教室長が、募集中・申し出ありの依頼の一覧を見られる。教室長は見るだけで、依頼も申し出もしない
- 理由：教室長が「今どの依頼で人が足りていないか」を把握できるようにする
- 決めた日：2026-10-18

### 引き受けの決め方

- 決定：他の講師が申し出て、依頼した講師が1人を選んだ時点で即成立する。教室長の承認はない。成立した代講は教室長の画面の一覧に出る
- 理由：誰に任せるかは依頼者が決めたい。教室長の承認を挟むと流れが長くなるので、MVPでは「知らせる」だけにする
- 決めた日：2026-10-11（第1案として）、2026-10-12（教室長の承認はMVPの後と確定）

### 申し出の制限

- 決定：自分の依頼には申し出られない。同じ人が1つの依頼に同時に出せる申し出は1つだけ（取り下げた後は、もう一度申し出られる）
- 理由：意味のない操作と二重登録を防ぐ。「同時に1つだけ」の制限はDBの一意制約で守る（[db.md](db.md)）
- 決めた日：2026-10-11〜12（設計週の初め。正確な日は記録なし）
- 補足：取り下げた申し出は行ごと消すので、取り下げた人はもう一度申し出られる

### 申し出の取り下げ

- 決定：MVPに入れる（US-11）。申し出た人は、選ばれる前なら自分の申し出を取り下げられる。成立した後は取り下げられない。申し出が0件になったら、依頼の状態は「申し出あり」から「募集中」に戻る。記録が必要になったら別テーブルを検討する（#25）
- 理由：急な用事で出られなくなった人が、選ばれる前に手を下ろせるようにする。成立の後に取り下げを許すと、「成立」から戻る遷移が要り、状態遷移が複雑になる
- 決めた日：2026-10-13（関連：#14）
- 取り下げた申し出は、行ごと消す。なので、取り下げた人は同じ依頼にもう一度申し出られる。取り下げの記録を残すかはMVPの後（#25）。決めた日：2026-10-18（関連：#14）

### 選ばれなかった人・取り消されたときの表示

- 決定：選ばれなかった人には「先に担当してくださる方がいたようです」程度の文を出し、理由は出さない。依頼が取り消されたら、申し出ていた人には「依頼が取り消されました」と出す
- 理由：講師どうしの関係を気まずくしない
- 決めた日：2026-10-11（選ばれなかった人）、2026-10-12（取り消し）

### 取り消し

- 決定：MVPに入れる。依頼の状態を「取り消し」にする条件付きUPDATE1文で行い、明示的なトランザクションは使わない
- 理由：1行の更新だけで済み、更新件数が0なら、今の状態を読み直して「もう取り消し済み」か「先に誰かが変えた」かを判断できる（[db.md](db.md)）
- 決めた日：2026-10-12

### 期限切れ

- 決定：授業開始時刻を過ぎた依頼は、データを書き換えず、一覧を出す問い合わせで除外して非表示にする。定期実行は使わない。一覧に出さないだけでなく、申し出・選ぶ・取り消す・取り下げるもサーバーで受け付けない
- 理由：削除や定期実行がなければ、作るものも壊れるものも減る。記録も残る。画面で隠すだけでは、APIを直接呼ばれると防げない
- 決めた日：2026-10-12（APIでも受け付けないことは 2026-10-13、関連：#14）
- 開始で判定する理由：授業が始まってから代わりが決まっても間に合わない（成立一覧だけは、授業中に確かめるため終了時刻まで出す）。
- 決めた日：2026-10-15（関連：#14）

### 教室長の成立一覧の表示期間

- 決定：成立した代講は、授業の終了時刻まで一覧に出す。終わった分を見られるようにする設定はMVPの後
- 理由：教室長が「今日これから誰が入るか」を授業中も確かめられるようにする
- 決めた日：2026-10-13（関連：#14）

### 引き受けの条件

- 決定：科目・学年での条件は設けない
- 理由：まず人員が確保できればよい
- 決めた日：2026-10-11

## MVPの範囲

| 箱 | 中身 |
| --- | --- |
| MVPでやる | 依頼の作成、申し出、申し出の取り下げ、依頼者が選んで成立、取り消し、期限切れの非表示、ログイン（LINE）、承認待ち、役割ごとの権限、教室長の成立一覧、役割の付与のスクリプト |
| MVPの後 | 通知（LINEなど）、教室長の承認、画面から役割を付ける機能、教室長が時限表を画面で入れる機能、メールとパスワードのログイン（#23）、メール送信（パスワード再設定など）、利用を止める（#15）、成立一覧で終わった分を見る設定、先着の自動確定、招待、カレンダー表示、複数教室、引き受け条件、Goへの書き直し |
| やらない | 生徒情報の管理、マイクロサービス、Kubernetes |

遅れたときは「MVPでやる」から「MVPの後」へ移す（週1回の振り返りで判断する。[workflow.md](workflow.md)）。
