# 認証・アカウント・役割

ログインの方法、新しい人の扱い、役割の付け方。ライブラリは Better Auth。

## 決まっていること

### ログインの方法と順番

- 決定：Better Auth を使う。MVPでは全員（講師・教室長・開発者）がLINEで入る。メールとパスワードのログインはMVPの後
- 理由：LINEログインがあれば、講師が新しいパスワードを覚えずに済む（実運用で使われやすい）。今の利用者は塾の講師・教室長と開発者1人だけで、全員LINEを使える。作るものを減らし、MVPを早く使ってもらう
- 影響：「先にメールとパスワードでセッションの仕組みを学ぶ」という学習の順番はなくなる。セッションとCookieはLINEログインを作るときに学ぶ
- 決めた日：2026-10-12（メールログインに関しては、2026-10-15）

### アカウント：承認待ち方式

- 決定：新しく登録した人（LINEログインを含む）は、教室長か開発者が承認するまで何も操作できない
- 理由：LINEアカウントは誰でも持っているので、そのままだと塾と関係のない人も入れてしまう。承認待ちなら、承認画面と「承認待ち」の状態だけで済む
- 決めた日：2026-10-12
- 変更（2026-10-13）：「承認を戻せば利用を止められる」は、MVPの後に回した（#15）。MVPでは講師が辞めることを想定しない。止めるときに「募集中の依頼」や「これからの担当」が宙に浮く問題があり、その扱いを含めて #15 で作る

### 役割と承認状態の持ち方

- 決定：Better Auth の `user` テーブルに列を足して持つ（`additionalFields`）。利用者が自分で書き換えられない設定（`input: false`）にする
- 理由：役割がセッションの型にも付き、JOINが要らない。教室長は講師を兼ねず1人1役割なので、列1つで足りる。複数教室に広げるときは、別テーブル（例：所属）へ移す
- 決めた日：2026-10-12
- 不確か：`input: false` の具体的な効き方は、作る前に Better Auth の公式ドキュメントで確認する

### 役割を付ける操作

- 決定：MVPでは画面もAPIも作らず、開発者が `make set-role` のようなスクリプトで付ける。画面から付ける機能はMVPの後
- 理由：
  1. 役割を付けるのは最初の1回と人が入れ替わるときだけで、画面・API・権限チェック・テストを作るのは重い
  2. 「役割を変えるAPI」は権限を上げる危ない操作なので、作らないのが最も安全
  3. 本番DBにSQLを手で打つより、スクリプトの中で確かめてから書き換える方が安全
- 最初の開発者：まずLINEで入り（承認待ちになる）、そのあとスクリプトで「承認済み」と `superadmin` を付ける。環境変数で最初から特別扱いする方法や、「最初に登録した人を自動で開発者にする」方法は採らない（ログインの処理に特別扱いが入り、権限を上げる入口になるため）。決めた日：2026-10-18
- 決めた日：2026-10-13（関連：#16）
- 補足（2026-10-15）：開発者もLINEで入り、`superadmin` の役割はスクリプトで付ける

スクリプトの約束（役割の付与、最初の開発者の承認、時限表の登録など、開発者が手で行う操作に共通）：

- 本番DBにSQLを手で打たない。必ずスクリプト経由で書き換える
- 手元の開発用DBも、できるかぎりスクリプト経由で書き換える。直接SQLを打つのは最小限にする
- スクリプトの中で、入力の値が正しいか（例：その人が存在するか、役割の値が正しいか、時限の時刻が正しいか）をzodで確かめてから書き換える
- スクリプトはリポジトリ（`scripts/`）に残し、何をしたかの記録にする
- 要確認：Better Auth の admin プラグインにも役割を変える機能がある。このプロジェクトは役割を `user` テーブルに自分で足した列で持つので、そのまま合うかは不確か。使う前に確認する
- 採らなかった案：「承認するときに役割も選ぶ」画面。ユーザーストーリー US-07 を少し広げれば作れるが、MVPの範囲を広げる判断になるため今回は採らない

### LINEログインのメール

- 決定：LINEの講師は、常に仮アドレス（LINEのユーザーIDから作る、`.invalid` で終わる届かないアドレス）を `user.email` に入れる。LINEからメールをもらえても使わない
- 理由：Better Auth は全ユーザーにメールを必要とするが、公式に仮アドレスの方法が案内されている。常に仮アドレスにすると、同じメールの人との自動の結びつきが起きず、持つ個人情報も減る
- 決めた日：2026-10-13（関連：#16）
- 付随して決めたこと：
  - メール確認を必須にする設定は、LINEログインに付けない（仮アドレスは確認メールを受け取れない）
  - 仮アドレスは画面に出さない
  - LINEの講師を見分ける鍵は、`account` テーブルの「プロバイダー＋ID」の組
- 不確か：LINEのユーザーを見分ける項目名と、仮アドレスを入れる具体的な設定（`mapProfileToUser` など）。作る前に公式で確認する（2026-10-15に調べた結果は下の「LINEログインの仮アドレス（調べたこと）」）

### メールの扱い

- 決定：メールの送受信はしない。メールはアカウントの識別とログインにだけ使う
- 理由：メール送信の仕組み（送信サービス、届かないときの対応）を持たずに済む
- 決めた日：2026-10-13（関連：#16）

### パスワードの再設定

- 決定：MVPではメールとパスワードのログインがないので、再設定もない。メールとパスワードのログインと一緒にMVPの後で決める
- 補足：Better Auth の再設定はメールでリンクを送る仕組み。MVPの後で実装を行う。
- 決めた日：2026-10-15（関連：#14 #23）

### LINEアカウントをなくした講師

- 決定：古いアカウントを止め、新しいアカウントを承認する運用で対応する。記録の引き継ぎはMVPの後
- 理由：引き継ぎの仕組みを作るより、承認待ち方式の運用で足りる
- 決めた日：2026-10-13（関連：#16）
- 補足（2026-10-15）：利用を止める機能はMVPの後（#15）なので、MVPの間は「古いアカウントを止める」が画面からはできない。前もって決めず、起きたときに「スクリプトで止める」か「止めずに置いておく」かを判断する

## LINEログインの仮アドレス（調べたこと、2026-10-15）

公式ドキュメントで確かめたことと、確かめきれていないこと。作る前にもう一度、公式で確認する。

確かめたこと：

- Better Auth は、すべてのユーザーにメールを必要とする。プロバイダーがメールを返さないと、`error=email_not_found` で失敗する（Better Auth: OAuth）
- その対策として、`mapProfileToUser` で「プロバイダーの変わらないID」から仮アドレスを作る方法が公式に案内されている。届かないドメイン（`.invalid`）を使うよう書かれている。公式の例は Discord・Apple・Microsoft で、LINE の例はない
- `mapProfileToUser` の戻り値は「利用者からの入力」として扱われる。`additionalFields` で `input: false` にした項目（役割・承認状態）は無視される。なので、LINEのプロフィールから役割や承認状態を書き換えられることはない
- `mapProfileToUser` で、アカウントの識別（`account` の「プロバイダー＋ID」）は変えられない
- 2回目以降のログインは、`account` の「プロバイダー＋ID」の組で見つける
- Better Auth の LINE の既定のスコープは `openid`・`profile`・`email`。`disableDefaultScope` で既定を外し、`scope` で必要なものだけにできる
- LINE の IDトークンには、必ず `sub`（ユーザーID）が入る。`email` は `email` スコープを付けたときだけ入る
- LINE のユーザーIDは、**プロバイダー（LINE Developers の「プロバイダー」）ごとに違う値**になる。同じ人でも、別のプロバイダーのチャネルでは別のIDになる（LINE: Getting user IDs）
- LINE からメールをもらうには、コンソールで「メールアドレスの取得権限」を申請する必要がある。利用者が同意画面で断ると `ACCESS_DENIED` になる

ここから考えられること（案。決定ではない）：

- メールを使わない決定なので、`email` スコープを外す（`disableDefaultScope` ＋ `scope: ["openid", "profile"]`）と、申請も個人情報も要らなくなる。既定のまま `email` を要求したとき、申請していないチャネルでどうなるかは不確か
- 仮アドレスは LINE の `sub` から作ることになる。Better Auth の LINE の `mapProfileToUser` に渡ってくるプロフィールの項目名（`sub` か別の名前か）は、公式ページに書かれていない（不確か。ソースコードか、実際に動かして確かめる）
- ユーザーIDはプロバイダーごとに変わるので、本番のLINEのチャネルは、最初に作ったプロバイダーから動かさない。移すと、全員が別人として扱われる

## LINEログインの準備（メモ）

- LINE Developers でLINEログインのチャネルを作り、チャネルIDとシークレットを受け取り、コールバックURLを登録する
- 作ったばかりのチャネルは「開発中」で、管理者とテスターに登録した人しかログインできない。誰でも使えるようにするには「公開」に切り替える（LINE公式）
- LINEからメールアドレスをもらうには申請が要る可能性がある。ただし、上の決定でメールは使わないので、申請はしない予定
