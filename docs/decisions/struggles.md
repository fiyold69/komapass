# 悩んだこと

決定の経緯を残す場所。何を決めようとしていて、何と比べ、なぜそれを選んだか。今の決定そのものは、それぞれのファイルにある（[README.md](README.md)）。

## 業務ルール

### 誰が代講を決めるか

- 状況：申し出た人の中から、誰が代講に入るかを決める仕組みが要った
- 比べた案：依頼した講師が1人を選ぶ／先着で自動的に決まる／教室長が承認する
- 決めたこと：依頼した講師が選んだ時点で即成立する。先着の自動確定と、教室長の承認はMVPの後
- 理由：誰に任せるかは依頼者が決めたい。教室長の承認を挟むと流れが長くなる。ヒアリングでも、教室長は「決まったら知らせてもらえれば十分」だった
- 関連：[business-rules.md](business-rules.md)、#17（2026-10-11 に第1案、10-12 に確定）

### 授業時刻を過ぎた依頼をどうするか

- 状況：授業が終わった依頼が、一覧に残り続けてしまう
- 比べた案：自動で削除する／「期限切れ」という状態にして書き換える／データは書き換えず、一覧を出すときに除外する。定期実行（決まった時間に動く処理）を使うかどうか
- 決めたこと：データは書き換えず、一覧を出す問い合わせで除外する。定期実行は使わない。さらに、一覧で隠すだけでなく、APIでも操作を受け付けない
- 理由：削除や定期実行がなければ、作るものも壊れるものも減り、記録も残る。画面で隠すだけでは、APIを直接呼ばれると防げないと、レビューで気づいた
- 関連：[business-rules.md](business-rules.md)、#14（2026-10-12 に非表示、10-13 にAPIでも受け付けない）

### 「授業時刻」は開始か、終了か

- 状況：期限切れの判定に使う「授業時刻」が、開始なのか終了なのかが決まっていなかった
- 比べた案：授業の開始時刻／終了時刻／開始の数十分前
- 決めたこと：依頼の一覧と操作の締め切りは開始時刻。教室長の成立一覧だけは終了時刻まで出す
- 理由：授業が始まってから代わりが決まっても間に合わない。成立一覧は、教室長が授業中に「今だれが入っているか」を確かめるために使う。目的が違えば、同じ「授業時刻」でも基準を変えてよい
- 関連：[business-rules.md](business-rules.md)、#14（2026-10-13 に成立一覧、10-15 に開始で確定）

### 申し出の取り下げを入れるか、取り下げた申し出をどうするか

- 状況：申し出たあとに急な用事で出られなくなる人がいる。取り下げたときに、申し出のデータをどう扱うか
- 比べた案：取り下げを入れない／入れる。入れるなら、申し出のレコードを消す／「取り下げ済み」として残す／別のテーブル（履歴）に移す
- 決めたこと：MVPに入れる。成立した後は取り下げられない。申し出が0件になったら「募集中」に戻る。取り下げた申し出はレコードごと消すので、もう一度申し出られる。記録を残すのはMVPの後
- 理由：成立の後まで許すと、「成立」から戻る遷移が要って状態が複雑になる。レコードを残すと、（依頼, 講師）の一意制約とぶつかり、もう一度申し出られない。記録を見る場面もMVPにはない。別テーブルは、持つ個人情報が増え、誰が見られるかまで決める必要がある
- 関連：[business-rules.md](business-rules.md)、[db.md](db.md)、#14、#25（2026-10-13 に取り下げを入れる、10-18 に消すと確定）

### 辞めた講師の利用を止める機能

- 状況：辞めた講師をアプリから外す機能（元のユーザーストーリー US-10）を、MVPに入れるか
- 比べた案：MVPに入れる／止められない講師を作る（募集中の依頼やこれからの担当がある人は止められない）／教室長以上が強制的に止める／MVPの後に回す
- 決めたこと：機能ごとMVPの後に回す。止められない講師や強制的に止める仕組みは、案として残した
- 理由：止めると、その人の募集中の依頼や、決まっていた担当が宙に浮く。その扱いまで作るのは重い。MVPでは講師が辞めることを想定しない
- 関連：[open-questions.md](open-questions.md)、#14、#15（2026-10-13）

### 同じコマへの二重の依頼

- 状況：ユーザーストーリーを書いていて、同じ講師が同じコマに2回依頼を出せるかが決まっていないと分かった
- 比べた案：出せない／出せる
- 決めたこと：有効な依頼は1つだけ（出せない）。ただし、DBで防ぐのが難しければ、MVPでは出せる状態でもよい
- 理由：二重に出すと、申し出が分かれて混乱する。一方で、取り消した依頼のレコードも残るので、単純な一意制約では「取り消した後の出し直し」ができなくなる。理想と、作る手間の落としどころを先に決めておいた
- 関連：[business-rules.md](business-rules.md)、[open-questions.md](open-questions.md)（2026-10-18）

### 教室長は依頼の一覧を見られるか

- 状況：一覧を見るユーザーストーリーが「講師として」だけだった
- 比べた案：講師だけ／講師と教室長
- 決めたこと：教室長も見られる。見るだけで、依頼も申し出もしない
- 理由：教室長が、今どの依頼で人が足りていないかを把握できるようにする
- 関連：[business-rules.md](business-rules.md)（2026-10-18）

### 時限表の入れ方

- 状況：期限切れの判定に時限表が要るのに、誰がどう入れるかが決まっていなかった
- 比べた案：開発者がスクリプトで入れる／教室長が画面で入れる
- 決めたこと：MVPでは開発者がスクリプトで入れる。教室長の画面はMVPの後
- 理由：MVPでは作るものを減らす
- 関連：[operations.md](operations.md)（2026-10-18）

## 認証・アカウント

### LINEログインで、誰を通すか

- 状況：LINEアカウントは誰でも持っているので、塾と関係のない人も入れてしまう
- 比べた案：シードで登録済みの講師とLINEを結びつける方式／承認待ち方式（新しく入った人は、承認されるまで何もできない）
- 決めたこと：承認待ち方式
- 理由：承認画面と「承認待ち」の状態だけで済む
- 関連：[auth.md](auth.md)（2026-10-12）

### LINEからメールアドレスがもらえない場合

- 状況：Better Auth は全ユーザーにメールを必要とするが、LINEからメールがもらえるとは限らない
- 比べた案：もらえたら使う、もらえなければ仮アドレス／常に仮アドレス
- 決めたこと：常に仮アドレス（LINEのユーザーIDから作る `.invalid` のアドレス）。メールの送受信もしない
- 理由：公式に仮アドレスの方法が案内されている。常に仮アドレスにすれば、同じメールの人との自動の結びつきが起きず、持つ個人情報も減る
- 関連：[auth.md](auth.md)、#16（2026-10-13）

### 役割をどうやって付けるか

- 状況：教室長や開発者の役割を、誰がどうやって付けるか
- 比べた案：役割を変える画面とAPIを作る／承認するときに役割も選ぶ画面（ユーザーストーリー US-07 を広げる）／開発者がスクリプトで付ける
- 決めたこと：MVPでは開発者がスクリプトで付ける。画面はMVPの後
- 理由：役割を付けるのは最初の1回と人が入れ替わるときだけで、画面・API・テストを作るのは重い。役割を変えるAPIは権限を上げる危ない入口なので、作らないのが最も安全。承認画面を広げる案は、MVPの範囲を広げる判断になるので採らなかった
- 関連：[auth.md](auth.md)、#16（2026-10-13）

### 最初の開発者を、誰が承認するか

- 状況：新しく入った人は承認待ちになるので、いちばん最初の開発者を承認できる人がいない
- 比べた案：スクリプトで承認と役割を付ける／環境変数で、特定のLINEのIDだけ最初から特別扱いする／最初に登録した人を自動で開発者にする／シードで入れておく
- 決めたこと：スクリプト。まずLINEで入り、そのあとスクリプトで承認と `superadmin` を付ける
- 理由：役割を付けるスクリプトと同じ仕組みで済み、本番DBに手でSQLを打たない約束にも合う。環境変数や自動の方法は、ログインの処理に特別扱いが入り、権限を上げる入口になる。最初の1人を自動にすると、他人に先に登録されたら乗っ取られる。シードはダミーデータだけと決めている
- 関連：[auth.md](auth.md)（2026-10-18）

### メールとパスワードのログインを、MVPに入れるか

- 状況：はじめは「先にメールとパスワードでセッションとCookieの仕組みを学び、後半にLINEログインを足す」予定だった
- 比べた案：メールとパスワードとLINEの両方／講師はLINE、教室長と開発者はメールとパスワード／全員LINE
- 決めたこと：MVPでは全員がLINEで入る。メールとパスワードのログインと、パスワードの再設定はMVPの後
- 理由：今の利用者は講師・教室長と開発者1人だけで、全員LINEを使える。作るものを減らし、MVPを早く使ってもらう。学習の順番は変わるが、セッションとCookieはLINEログインを作るときに学べる
- 関連：[auth.md](auth.md)、#14、#23（2026-10-12 に最初の予定、10-13 にパスワード再設定をスクリプトに、10-15 に全員LINEと確定）

### LINEアカウントをなくした講師

- 状況：LINEアカウントをなくすと、新しいアカウントは別人として扱われる
- 比べた案：記録を引き継ぐ仕組みを作る／古いアカウントを止め、新しいアカウントを承認する運用
- 決めたこと：運用で対応する。利用を止める機能がMVPの後になったので、MVPの間は、起きたときに「スクリプトで止める」か「止めずに置いておく」かを判断する
- 理由：引き継ぎの仕組みを作るより、承認待ち方式の運用で足りる
- 関連：[auth.md](auth.md)、#16（2026-10-13、10-15）

## DB

### PostgreSQL から MySQL へ

- 状況：はじめはPostgreSQLの前提で設計していた
- 比べた案：PostgreSQL／MySQL
- 決めたこと：MySQL
- 理由：インターン先と同じなので、インターンと個人開発の学びが互いに効き、聞ける相手もいる
- 影響：設計のうち4つのやり方が変わった。部分一意インデックスがないので「確定は1件だけ」を確定した講師の列1つで守る、`RETURNING` がないので条件付きUPDATEの更新件数で判断する、日時は整数（`bigint`）で持つ、分離レベルの既定がRepeatable Readになる
- 関連：[db.md](db.md)（2026-10-12）

### 二重クリックと「更新件数が0」

- 状況：はじめは「条件付きUPDATEの更新件数が0なら、先に誰かが変えた＝失敗」と決めていた。しかし、二重クリックでは、2回目が更新件数0になり、利用者が望んだ結果なのにエラーが出てしまう
- 比べた案：0なら必ず失敗／0のときは今の状態を読み直し、自分の操作がもう反映されていれば成功とする／画面でボタンを押せなくするだけ
- 決めたこと：読み直して判断する（冪等にする）。画面の対策もするが、それだけには頼らない
- 理由：通信の再送などで、同じリクエストが2回届くことがある。サーバー側で守らないと防げない
- 関連：[db.md](db.md)、`docs/concurrency-cases.md`、#14

### 同時操作を、MVPでどこまで守るか

- 状況：同時操作のケースを11個挙げたが、全部をMVPで守るのは重い
- 比べた案：全部守る／ケースごとに「起きやすさ」「起きたときの困り方」「防ぐ手間」で比べて選ぶ
- 決めたこと：比べて選んだ。二重クリック・二重の申し出・取り下げと選ぶの重なりなどはMVP、申し出と選ぶ・取り消すの同時、2人同時の取り下げなどはMVPの後
- 理由：MVPの規模（1つの塾、講師は数十人ほど）では、ほぼ起きないものもある。手間の割に効果が小さいものは後に回す
- 関連：`docs/concurrency-cases.md` の「MVPでやるか（検討の記録）」、#14

## 公開先と運用

### 公開先をどこにするか

- 状況：完成後に塾で実際に使ってもらうので、「止まらない」「データが消えない」が大事
- 比べた案：Railway Hobby／Google Cloud／Cloudflare Workers／AWS／Render＋Aiven（無料）
- 決めたこと：Railway Hobby（月5ドル）。ほかはMVPの後の発展課題か、見送り
- 理由：無料枠は、使われないと止まったり、期限で消えたりして実運用に向かない。RailwayはAPIとMySQLを同じ場所に置け、手間が少ない。ただし、まだ変わる可能性があるので、ADRには書いていない
- 関連：[operations.md](operations.md)（2026-10-12）

### コマンドの入口を Makefile にするか

- 状況：手元で立ち上げる・テストする・スクリプトを動かすなどの入口を、どうまとめるか

## 進め方・記録

### 決定をどこに置くか

- 状況：決定が CLAUDE.md と、作者だけが見られる別の文書に分かれて書かれ、食い違い始めた。新しいチャットやセッションに移ると、AIが経緯を知らないまま答えることもあった
- 比べた案：CLAUDE.md に書き足す／作者だけが見られる別の文書に書く／リポジトリの `docs/decisions/` にまとめる
- 決めたこと：`docs/decisions/` を正本にし、CLAUDE.md はその要約にする
- 理由：1か所にまとめれば食い違わない。リポジトリにあれば、どのセッションのAIも読めるので、会話の記憶に頼らずに済む
- 関連：[README.md](README.md)、#16、#18（2026-10-13）

### 会話で先に決まったことと、正本のずれ

- 状況：実際には、会話やPRの中で先に決まり、`docs/decisions/` があとから追いつくことが多い。その間は、古い決定のほうが正として扱われてしまう
- 比べた案：決定を変えるPRで、正本も同時に直す／ルールを変える
- 決めたこと：決定を変えるPRで、`docs/decisions/` と CLAUDE.md（と関係する設計書）を同時に直す。マージまでは、会話で決めたことは「案」
- 理由：マージした瞬間に正本と実際の決定がそろうので、ずれている期間がPRの中だけになる
- 関連：[README.md](README.md)（2026-10-18）

### 決定の書き方（経緯をどこに残すか）

- 状況：決定のファイルに「決めた日」「変更（日付）」「追記」や「決定の履歴」の表が増え、今の決定が読みにくくなった
- 比べた案：履歴を本文に書き続ける／今の決定だけを書き（Wikiのように）、経緯は別にする。経緯は gitとPR に任せる／悩んだこととしてまとめる／GitHub Wiki に書く
- 決めたこと：決定のファイルは今の決定だけ。経緯はこのファイル（悩んだこと）にジャンル分けしてまとめる。大きな方針転換はADR。未決は open-questions.md にだけ書き、決まったら消す。決定の中に未決があるときは、リンクだけを置く。書式は決定ではなく、悩んだことに使う
- 理由：今の決定がすぐ読める。悩んだことは、面接で「大変だったこと」を聞かれたときにそのまま使える。gitやPRをさかのぼらなくて済む。GitHub Wiki はPRでレビューできず、AIも読めない
- 関連：[README.md](README.md)、#24（2026-10-18）

### ブランチ名に入れるIssue番号

- 状況：PR #14 は、ブランチ名が親Issueの番号（#1）で、閉じるのは子Issue（#13）だった。どちらの番号を入れるかが決まっていなかった
- 比べた案：親の番号／子の番号。作業の途中で子Issueに分けたくなったとき、ブランチの上にさらにブランチ（孫ブランチ）を切るか
- 決めたこと：片付けるIssue（子があれば子）の番号を入れる。ブランチは基本的にmainから切り、孫ブランチは避ける。ただし、子Issueに分けるたびに毎回マージするとは限らず、同じブランチでまとめて片付けてもよい
- 理由：`Closes #番号` とそろい、ブランチ名を見ればどのIssueを閉じるか分かる。孫ブランチは、親をSquash mergeすると古いコミットが残り、付け替え（`git rebase --onto`）が要って管理が大変になる。一方で、毎回マージしていると手間がかかりすぎる
- 関連：[workflow.md](workflow.md)、#14（2026-10-18）

### 設計に時間をかけすぎた

- 状況：設計週（10/12〜10/18）の予定だったが、決定とユーザーストーリーの整理に時間がかかり、状態遷移図・ER図・API一覧・画面一覧まで終わらなかった。本選考も始まっている
- 比べた案：設計を全部終えてから作る／図はそれを使うフェーズの直前に書き、手を動かす作業を先に始める
- 決めたこと：図は使う直前に書く（画面一覧はフェーズ1の前、状態遷移図・ER図・API一覧はフェーズ2の前）。完璧より、作りながら直す
- 理由：フェーズ0（JavaScriptの土台、リポジトリの土台）には図が要らない。手を動かす作業を止めないことを優先する
- 関連：[workflow.md](workflow.md)（2026-10-18 の振り返り）

### チャットとClaude Codeの使い分け

- 状況：考えて決めることと、リポジトリの中で手を動かすことを、どちらのAIでやるか
- 比べた案：役割をきっちり分ける／目安にとどめる
- 決めたこと：チャットは「考えて決める場所」、Claude Code は「リポジトリの中で手を動かす場所」を目安にする。厳密には分けない。1人で開発していてレビューしてくれる人がいないので、頼んだときは Claude Code がPRにレビューを残す
- 理由：記録が残っていない（要確認）
- 関連：[workflow.md](workflow.md)（2026-10-13 に使い分け、10-15 に目安とした）

## 公開とセキュリティ

### 公開して問題ないかの点検

- 状況：リポジトリを公開する前に、塾が特定されないか、事故が起きないかを点検した
- 比べた案：役割の呼び方が勤め先に固有の言葉かもしれなかったので、①今のファイル・Issue・コメントだけ一般的な言葉に直す／②gitの履歴まで書き換える／③公開用に新しいリポジトリを作る
- 決めたこと：①。役割の呼び方を「教室長」にそろえ、ヒアリングの回答も一般的な書き方に直した。編集履歴の古い版も消した。ヒアリングの生の記録はリポジトリの外に置いた
- 理由：その言葉だけで塾は特定できず、古い履歴までさかのぼって探す人はまずいない。履歴を書き換えると、ブランチとPRの整合性が崩れる。新しいリポジトリにすると、IssueとPRのやり取りの記録（ポートフォリオとしての価値）を失う
