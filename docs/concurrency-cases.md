# 同時操作のケース

依頼と申し出は、複数の人が同じデータをほぼ同時に操作することがある。
このファイルでは、起こりうる組み合わせと、そのとき期待する結果をまとめる。

- ユーザーストーリー（docs/user-stories.md）には、利用者に見えるものだけを書く
- テストでは、このファイルの全ケースを確かめる
- どのくらい起きるかは推測。ヒアリング（#3）で確かめる

## 登場人物とデータ

| 記号 | 説明 |
| --- | --- |
| 講師A | 依頼Rを出した講師（依頼者） |
| 講師B | 依頼Rにすでに申し出ている講師 |
| 講師C | 依頼Rにすでに申し出ている、Bとは別の講師 |
| 講師D | 依頼Rにまだ申し出ていない講師 |
| 依頼R | 講師Aが出した依頼。特に書かない限り、状態は「申し出あり」 |

## 守り方の共通ルール

- 状態の変更（選ぶ・取り消す・取り下げる）は、条件付きUPDATEで行う
  - 例：「依頼Rの状態が申し出ありで、かつ「授業開始時刻の前なら、成立に変える」
- 更新件数が0のとき、サーバーは「先に状態が変わった」と判断し、失敗を返す
- 申し出の重複は、申し出テーブルの（依頼, 講師）の一意制約で防ぐ
- 授業時刻の判定は、画面ではなくサーバーで行う

## 優先度：高（ユーザーストーリーに書く）

### ケース1：講師Aが「選ぶ」を二重に押す

| 項目 | 内容 |
| --- | --- |
| 操作① | 講師Aが、依頼Rで、講師Bを選ぶ |
| 操作② | 講師Aが、依頼Rで、講師Bをもう一度選ぶ（二重クリック） |
| 期待する結果 | 操作①だけが成功する。依頼Rは「講師Bで成立」のまま変わらない |
| 講師Aに見えるもの | 「成立しました」と1回だけ表示される。エラー画面にはならない |
| 守る仕組み | 条件付きUPDATE |

### ケース2：講師Aが「取り消す」を二重に押す

| 項目 | 内容 |
| --- | --- |
| 操作① | 講師Aが、依頼Rを取り消す |
| 操作② | 講師Aが、依頼Rをもう一度取り消す（二重クリック） |
| 期待する結果 | 操作①だけが成功する。依頼Rは「取り消し」のまま変わらない |
| 講師Aに見えるもの | 「取り消しました」と1回だけ表示される |
| 守る仕組み | 条件付きUPDATE |

### ケース3：講師Dが「申し出る」を二重に押す

| 項目 | 内容 |
| --- | --- |
| 操作① | 講師Dが、依頼Rに申し出る |
| 操作② | 講師Dが、依頼Rにもう一度申し出る（二重クリック） |
| 期待する結果 | 申し出は1件だけ記録される |
| 講師Aに見えるもの | 申し出た人の一覧に、講師Dの名前が1回だけ表示される |
| 守る仕組み | （依頼, 講師）の一意制約 |

### ケース4：講師Dの申し出と、講師Aの「選ぶ」が重なる

| 項目 | 内容 |
| --- | --- |
| 操作① | 講師Dが、依頼Rに申し出る |
| 操作② | 講師Aが、依頼Rで、講師Bを選ぶ |
| 期待する結果（②が先） | 依頼Rは「講師Bで成立」になる。講師Dの申し出は失敗する |
| 期待する結果（①が先） | 講師Dの申し出は記録される。その後、依頼Rは「講師Bで成立」になり、講師Dは選ばれなかった人として扱われる |
| 講師Dに見えるもの | どちらの順でも「先に担当してくださる方がいたようです」 |
| 守る仕組み | 申し出るときに、依頼Rの状態を確認する ＋ 条件付きUPDATE |

### ケース5：講師Dの申し出と、講師Aの「取り消す」が重なる

| 項目 | 内容 |
| --- | --- |
| 操作① | 講師Dが、依頼Rに申し出る |
| 操作② | 講師Aが、依頼Rを取り消す |
| 期待する結果（②が先） | 依頼Rは「取り消し」になる。講師Dの申し出は失敗する |
| 期待する結果（①が先） | 講師Dの申し出は記録される。その後、依頼Rは「取り消し」になる |
| 講師Dに見えるもの | どちらの順でも「依頼が取り消されました」 |
| 守る仕組み | 申し出るときに、依頼Rの状態を確認する ＋ 条件付きUPDATE |

### ケース6：講師Aが、授業開始時刻の直前に選ぶ

| 項目 | 内容 |
| --- | --- |
| 操作① | 講師Aが、依頼Rで、講師Bを選ぶ |
| 同時に起きること | 依頼Rの授業開始時刻を過ぎる |
| 期待する結果 | サーバーに届いた時点で授業開始時刻を過ぎていれば、選ぶ操作は失敗する |
| 講師Aに見えるもの | 「授業開始時刻を過ぎたため、操作できません」 |
| 守る仕組み | 条件付きUPDATEの条件に、授業開始時刻を含める |

## 優先度：低（テストだけで確かめる）

### ケース7：講師Aが、別のタブで「選ぶ」と「取り消す」を同時に行う

| 項目 | 内容 |
| --- | --- |
| 操作① | 講師Aが、依頼Rで、講師Bを選ぶ |
| 操作② | 講師Aが、依頼Rを取り消す |
| 期待する結果 | どちらか一方だけが成功する。依頼Rは「成立」か「取り消し」のどちらかになり、両方にはならない |
| 守る仕組み | 条件付きUPDATE |

### ケース8：講師Aが、別のタブで2人をほぼ同時に選ぶ

| 項目 | 内容 |
| --- | --- |
| 操作① | 講師Aが、依頼Rで、講師Bを選ぶ |
| 操作② | 講師Aが、依頼Rで、講師Cを選ぶ |
| 期待する結果 | どちらか一方だけが成功する。確定した講師は1人だけ |
| 守る仕組み | 条件付きUPDATE ＋ 依頼テーブルの「確定した講師」の列 |

### ケース9：講師Bの取り下げと、講師Aの「選ぶ」が重なる

| 項目 | 内容 |
| --- | --- |
| 操作① | 講師Bが、依頼Rへの申し出を取り下げる |
| 操作② | 講師Aが、依頼Rで、講師Bを選ぶ |
| 期待する結果 | 取り下げが先なら、選ぶは失敗（申し出ていない人は選べない）。選ぶが先なら、取り下げは失敗（成立した後は取り下げられない） |

### ケース10：最後の申し出が、すべて取り下げられる

| 項目 | 内容 |
| --- | --- |
| 操作① | 講師Bが、依頼Rへの申し出を取り下げる |
| 操作② | 講師Cが、依頼Rへの申し出を取り下げる |
| 期待する結果 | 両方が成功し、依頼Rは『募集中』に戻る |
| 未決 | 取り下げた人がもう一度申し出られるか（一意制約とぶつかる可能性がある） |

### ケース11：講師Aが操作している最中に、利用が止められる

| 項目 | 内容 |
| --- | --- |
| 操作① | 講師Aが、依頼Rで、講師Bを選ぶ |
| 操作② | 教室長が、講師Aの利用を止める |
| 未決 | 利用を止めた後に届いた講師Aの操作を、失敗にするか |

## MVPでやるか（検討の記録）

MVPの規模（1つの塾、講師は数十人ほど）を前提に、「起きやすさ」「起きたときの困り方」「防ぐ手間」で比べた。

| ケース | 起きやすさ | 起きたときの困り方 | 防ぐ手間 | 判断 |
| --- | --- | --- | --- | --- |
| 1・2 二重クリック | 高い（スマホで2回タップは普通に起きる） | エラーが出て混乱する | 小（ボタンを押せなくする＋サーバーで読み直す） | MVP |
| 3 二重の申し出 | 高い | エラーが出て混乱する | 小（一意制約で断られたら、成功として返す） | MVP |
| 6・7・8 時刻ぎりぎり、選ぶと取り消しの同時、2人同時に選ぶ | 低い | 大（二重成立など） | ほぼ0（条件付きUPDATEで自然に防げる） | MVP（テストは後でもよい） |
| 4・5 申し出と、選ぶ・取り消すの同時 | 低い | 小（結局「先に担当…」「取り消されました」が出る） | 中（ロックが要る） | MVPの後 |
| 9 取り下げと選ぶ | 意外と高い（古い画面のまま選べてしまう） | 大（取り下げた人が担当になる） | 小〜中（選ぶ条件に「申し出がまだあること」を入れる） | MVP |
| 10 2人同時の取り下げ | とても低い | 小（「申し出あり」のまま残る） | 中（「申し出あり」を保存しない設計なら0） | MVPの後（状態遷移図 #5 で再検討） |
| 11 操作中に利用を止める | — | — | — | MVPの後（#15） |
