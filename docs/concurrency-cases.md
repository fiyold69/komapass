# 同時操作のケース

依頼と申し出は、複数の人が同じデータをほぼ同時に操作することがある。
このファイルでは、起こりうる組み合わせと、そのとき期待する結果をまとめる。

- ユーザーストーリー（docs/user-stories.md）には、利用者に見えるものだけを書く
- テストでは、このファイルの全ケースを確かめる
- どのくらい起きるかは推測。ヒアリング（#3）で確かめる

## 登場人物とデータ

| 記号 | 説明 |
|---|---|
| 講師A | 依頼Rを出した講師（依頼者） |
| 講師B | 依頼Rにすでに申し出ている講師 |
| 講師C | 依頼Rにすでに申し出ている、Bとは別の講師 |
| 講師D | 依頼Rにまだ申し出ていない講師 |
| 依頼R | 講師Aが出した依頼。特に書かない限り、状態は「申し出あり」 |

## 守り方の共通ルール

- 状態の変更（選ぶ・取り消す・取り下げる）は、条件付きUPDATEで行う
  - 例：「依頼Rの状態が申し出ありで、かつ授業時刻の前なら、成立に変える」
- 更新件数が0のとき、サーバーは「先に状態が変わった」と判断し、失敗を返す
- 申し出の重複は、申し出テーブルの（依頼, 講師）の一意制約で防ぐ
- 授業時刻の判定は、画面ではなくサーバーで行う

## 優先度：高（ユーザーストーリーに書く）

### ケース1：講師Aが「選ぶ」を二重に押す

| 項目 | 内容 |
|---|---|
| 操作① | 講師Aが、依頼Rで、講師Bを選ぶ |
| 操作② | 講師Aが、依頼Rで、講師Bをもう一度選ぶ（二重クリック） |
| 期待する結果 | 操作①だけが成功する。依頼Rは「講師Bで成立」のまま変わらない |
| 講師Aに見えるもの | 「成立しました」と1回だけ表示される。エラー画面にはならない |
| 守る仕組み | 条件付きUPDATE |

### ケース2：講師Aが「取り消す」を二重に押す

| 項目 | 内容 |
|---|---|
| 操作① | 講師Aが、依頼Rを取り消す |
| 操作② | 講師Aが、依頼Rをもう一度取り消す（二重クリック） |
| 期待する結果 | 操作①だけが成功する。依頼Rは「取り消し」のまま変わらない |
| 講師Aに見えるもの | 「取り消しました」と1回だけ表示される |
| 守る仕組み | 条件付きUPDATE |

### ケース3：講師Dが「申し出る」を二重に押す

| 項目 | 内容 |
|---|---|
| 操作① | 講師Dが、依頼Rに申し出る |
| 操作② | 講師Dが、依頼Rにもう一度申し出る（二重クリック） |
| 期待する結果 | 申し出は1件だけ記録される |
| 講師Aに見えるもの | 申し出た人の一覧に、講師Dの名前が1回だけ表示される |
| 守る仕組み | （依頼, 講師）の一意制約 |

### ケース4：講師Dの申し出と、講師Aの「選ぶ」が重なる

| 項目 | 内容 |
|---|---|
| 操作① | 講師Dが、依頼Rに申し出る |
| 操作② | 講師Aが、依頼Rで、講師Bを選ぶ |
| 期待する結果（②が先） | 依頼Rは「講師Bで成立」になる。講師Dの申し出は失敗する |
| 期待する結果（①が先） | 講師Dの申し出は記録される。その後、依頼Rは「講師Bで成立」になり、講師Dは選ばれなかった人として扱われる |
| 講師Dに見えるもの | どちらの順でも「先に担当してくださる方がいたようです」 |
| 守る仕組み | 申し出るときに、依頼Rの状態を確認する ＋ 条件付きUPDATE |

### ケース5：講師Dの申し出と、講師Aの「取り消す」が重なる

| 項目 | 内容 |
|---|---|
| 操作① | 講師Dが、依頼Rに申し出る |
| 操作② | 講師Aが、依頼Rを取り消す |
| 期待する結果（②が先） | 依頼Rは「取り消し」になる。講師Dの申し出は失敗する |
| 期待する結果（①が先） | 講師Dの申し出は記録される。その後、依頼Rは「取り消し」になる |
| 講師Dに見えるもの | どちらの順でも「依頼が取り消されました」 |
| 守る仕組み | 申し出るときに、依頼Rの状態を確認する ＋ 条件付きUPDATE |

### ケース6：講師Aが、授業時刻の直前に選ぶ

| 項目 | 内容 |
|---|---|
| 操作① | 講師Aが、依頼Rで、講師Bを選ぶ |
| 同時に起きること | 依頼Rの授業時刻を過ぎる |
| 期待する結果 | サーバーに届いた時点で授業時刻を過ぎていれば、選ぶ操作は失敗する |
| 講師Aに見えるもの | 「授業時刻を過ぎたため、操作できません」 |
| 守る仕組み | 条件付きUPDATEの条件に、授業時刻を含める |

## 決めることの優先順位

あとで変えると作り直しが大きいもの（DB → API → 画面）から先に決める。

### 1. 申し出の取り下げを、DBでどう持つか（ER図 #6 の前に決める）
- 決めること
  - 講師Bが取り下げたとき、申し出の行を消すのか、「取り下げ済み」の状態として残すのか
  - 取り下げた講師は、同じ依頼にもう一度申し出られるか
- 先に決める理由
  - （依頼, 講師）の一意制約と直接ぶつかる。行を残したまま再申し出を許すと、制約を変える必要がある
  - テーブルの形が変わるので、マイグレーションを作った後だと直すのが大変
- 関わるケース：9、10

### 2. 「授業時刻」は開始か、終了か（ER図 #6・API一覧 #7 の前に決める）
- 決めること
  - 依頼の一覧から消す時刻、操作できなくなる時刻を、授業の開始にするか終了にするか
  - 成立一覧は「授業終了まで表示する」と決めている。依頼の一覧や操作のほうも、同じ基準にするか
- 先に決める理由
  - 一覧を出す問い合わせと、条件付きUPDATEの条件の両方に入る
  - 時限表テーブルに、開始と終了のどちらの列が要るかが変わる
- 関わるケース：6、US-02、US-04、US-05、US-09

### 3. 日時の単位（秒かミリ秒か）（ER図 #6 の前に決める）
- 決めること：bigintで持つ日時を、秒にするかミリ秒にするか
- 先に決める理由：すべての日時の列と、時刻を比べる処理に関わる。途中で変えると、全体を直すことになる
- 関わるケース：6（時刻の判定）

### 4. 申し出が0件になったときの状態（API一覧 #7 の前に決める）
- 決めること：最後の申し出が取り下げられたら、依頼Rを「申し出あり」から「募集中」に戻すか
- 先に決める理由：状態遷移図（#5）と、取り下げのAPIの処理が変わる
- 関わるケース：10

### 5. 成立した後に取り下げられるか（状態遷移図 #5 の前に決める）
- 決めること：講師Bが選ばれた後でも、申し出を取り下げられるか
- 先に決める理由：取り下げられるなら、「成立」から戻る矢印が状態遷移図に増える。依頼テーブルの「確定した講師」の列を空に戻す処理も要る
- 関わるケース：9

### 6. 失敗したときにAPIが返すもの（API一覧 #7 で決める）
- 決めること
  - 「先に状態が変わった」ときのHTTPステータス（例：409）
  - 「授業時刻を過ぎた」ときのHTTPステータス
  - 応答の形
- 後でよい理由：DBの形には関わらない

### 7. 利用を止められた人の操作（ほぼ決まっている）
- 権限チェックはリクエストごとにサーバーで行う決まりなので、止めた後に届いた操作は自然に失敗する
- 確かめること：その動きで問題ないか
- 関わるケース：11

### 8. 画面に出す文言（実装のときに決める）
- 決めること：「先に状態が変わった」「授業時刻を過ぎた」ときに、利用者に表示する文
- 後でよい理由：あとで変えても、影響は画面の中だけ

## 進め方のメモ
- 1〜3は、ER図（#6）を始める前に決める。決めないとER図が書けない。設計週（10/18まで）の残りが少ないので、まずこの3つを片付ける
- 1（取り下げをDBでどう持つか）と5（成立した後に取り下げられるか）は、どちらも取り下げのルール。同じタイミングで一緒に決めると、話がぶれない
- 決めたことは、CLAUDE.mdの「業務ルール」に移す。CLAUDE.mdを直さないと、AIが古いルールのまま答えてしまう
- 後回しにしたこと（例：LINEからメールアドレスがもらえない場合）は、CLAUDE.mdの「未決事項」に残す
- 「講師Aに見えるもの」の文言は仮のもの。CLAUDE.mdで決まっているのは、選ばれなかった人への文（「先に担当してくださる方がいたようです」）と、取り消されたときの文（「依頼が取り消されました」）だけ
- ケース4・5で申し出が先に届いた場合、講師Dは申し出が成功した直後に「選ばれなかった」「取り消された」と知ることになる。この流れでよいか確かめる
- どのケースがどのくらい起きるかは推測。ヒアリング（#3）で確かめる
